## Findings requiring attention

### FIN-01 — Top-up charges omit the base booking's item arithmetic check (P2)

`NTEStripeBookingService.cls:275–286` accepts a positive unpaid top-up after checking the **base** `savedPriceError`. `BOOKING_FIELDS` at lines 8–16 does not load `NTE_Top_Up_Staff_Unit_Price__c`; the top-up fingerprint at lines 288–294 also omits that unit price. Request construction at lines 307–314 trusts the saved top-up total. The base equivalent explicitly validates quantity × saved unit price = component total in `NTEExhibitorApprovalEmailService.cls:425–453`.

Reproduction to add as an isolated regression, not against retained fixtures: create a valid converted application; save two top-up staff at £50 each but an inconsistent net total of £150; call the normal `TOP_UP` finance action with valid Stripe configuration. Current eligibility accepts the row and constructs a £180 request, despite the recorded components implying £120 including VAT. Likewise, changing only a queued top-up's unit price does not change its fingerprint. These fields are editable by NTE Management users (`NTE_Management_User.permissionset-meta.xml:1022–1025,1242–1250`). The ordinary supplementary form calculates consistent data (`NTEUpdateSubmissionService.cls:341–344`), so this is a downstream saved-data integrity gap, not a claim that normal form input currently misprices.

Add the saved top-up unit price to the read/fingerprint and validate its positive whole quantity and arithmetic before sending. Use the **saved** unit price; do not reprice accepted history against today's catalogue or add checklist/stage gates. Verify the failure leaves the existing request, payment and checklist history intact.

### FIN-02 — Changed top-up totals can silently change the value recorded as paid (P2, reconciliation behaviour needs an explicit decision)

After an issued top-up request for £100 net / £120 gross, edit the current top-up to £150 net / £180 gross. Its existing Stripe link remains fixed at £120. `NTE_MasterPanelController.cls:789–793` records `TOP_UP_PAYMENT_RECEIVED` without consulting the saved request or reporting a discrepancy. Its pricing check at lines 757–758 validates only the base status/total (`1261–1268`). The paid value uses the current top-up amount (`485–486`, `1195–1197`), so the ordinary action can show £180 paid with no indication that the linked Stripe request was £120. No top-up payment-confirmation email runs; the base confirmation's saved/current amount check (`NTEExhibitorApprovalEmailService.cls:336–338`) does not cover this route.

This does **not** prove an incorrectly collected payment or an error in preserved fixtures. An operator may have genuinely collected the revised amount by bank transfer. The issue is that the ordinary receipt action does not distinguish that reconciliation from receipt of the original fixed Stripe charge. Surface the saved/current discrepancy and define how staff explicitly record a reconciled manual receipt; preserve the ability to record real money received and do not silently overwrite the old request. Add an isolated changed-top-up receipt case checking the warning/result, original request and reported paid value.

## Controls supported by source and preserved evidence

- Conversion's after-update guard rejects missing/already-used targets before the active copy Flow persists its updates. The Flow invokes pricing, copies the current application with VAT and classifies the exact converted Account/Contact; it contains no booking-email or Stripe action. Names receive the saved event-code suffix. Existing native M04/M05 evidence covers distinct Opportunities sharing Account/Contact and name.
- Base and top-up use separate operation keys (`:Booking`, `:TopUp`), amounts and receipt facts. Creation retries reuse their saved payload/resource IDs. Unknown creation outcomes older than 23 hours require reconciliation. Already-paid/cancelled requests and changed booking/recipient/mode/account snapshots are held; saved links are verified before delivery.
- The Stripe client verifies expected account and test/live balance mode before writes, validates fixed GBP pence and matching VAT arithmetic, and reads back the price, line count, amount, currency, URL, active state, card-only methods, disabled automatic tax/invoicing/adjustable quantities and one-completed-checkout restriction. Operator permissions expose payment requests read-only. No credential content was read or copied by this review.
- Booking confirmation uses the exact current Primary Contact, fails without a usable single primary and has a unique booking-level dispatch key. Notification failure preserves the recorded payment. Top-up receipt does not queue another base confirmation. Requirements ticks are independent; accepted sends do not tick them.

Current application pricing forces 20%; `NTEVatTest.cls:43–60` deliberately preserves separately saved historical rates and rounding. Do not classify support for a saved 17.5% rate as an arithmetic defect or silently backfill it.

## Retained decisions and boundaries

Do not add a sent-refiner gate to manual receipt solely because `updateMilestone` can be invoked outside the current UI. The older explicit rule/test permits confirmation after a failed provisional send (`NTEBookingPaymentEmailTest.cls:164–188`); the latest refiner design controls where actions appear. Keep that distinction clear in tests and operational documentation.

The existing handover already records that changed base totals can block automatic confirmation, and that changing stage or recording payment does not close an outstanding Stripe link (`NTE_STRIPE_CLIENT_HANDOVER_2026-09-11.md:140–146`). Manual transfer, cancellation/refund reconciliation and closing superseded unpaid links remain deliberate finance operations. This review does not authorise automatic link cancellation, refunds, historical repricing, a new ledger, client/live activation or a Flow migration.

**Unresolved base-payment reconciliation limitation, retained explicitly for this bounded release:** `NTEExhibitorApprovalEmailService.cls:337–338` rejects a booking-confirmation render when the current base net/gross differs from the saved Booking Stripe request. `NTEStripeBookingService.paymentForEmail` loads that saved request independently of the current Payment Method, so selecting Bank transfer does not bypass the render exception. The reviewed receipt action can record the full current amount after a reconciled manual transfer, including after a failed provisional email, and retains the historical Stripe request. Its queued confirmation can nevertheless fail during rendering and require finance attention. Changing confirmation amount semantics, rewriting the original request, closing its link, or adding a reconciliation ledger is outside this patch. Top-up receipt continues to preserve the single existing base confirmation.
