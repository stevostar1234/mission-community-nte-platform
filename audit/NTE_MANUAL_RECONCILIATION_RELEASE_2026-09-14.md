# Manual price reconciliation and Requirements follow-up — 14 September 2026

This follow-up implements the owner's selected rules after the completed 13–14 September manual-finance release. It does not repeat the earlier applicant submissions, payment-link sends, payments or fixture cleanup. MMUAT and the existing canonical preview are the release targets; production remains separate.

## Implemented behaviour

- Staff enter a revised base booking total **including VAT in Opportunity Amount**. An Amount-only edit derives the rounded net and VAT, and replaces a separate **Booking adjustment (ex VAT)** relative to the original component prices. Original space/package, socket and staff prices stay intact. A later Amount edit recalculates the adjustment from those original items, rather than compounding the previous adjustment. Existing receipt facts, requested finance documents, top-ups and Stripe requests are preserved.
- For example, an original £799 net / £958.80 gross booking revised to £1,080.01 becomes £900.01 net, £180 VAT and a £101.01 adjustment. The adjustment appears in the current booking email summary, Salesforce pricing section and relevant reports. Amount remains the gross base total; the separate top-up is counted once.
- Full waivers to £0 are supported for both exhibitor and partner/sponsor bookings. A new explicit free-confirmation fact distinguishes a previously sent provisional email from an accepted free confirmation. A waived partner has its own appropriate confirmation template. The original item price and negative adjustment reconcile to zero; the email contains no historical Stripe payment button. Original payment/send history is not erased. A failed paid confirmation can also be retried as a waived confirmation using the same dispatch, without sending a duplicate.
- **Booking payment received** confirms the current agreed booking even when an earlier Stripe request has another amount. The confirmation path does not contact Stripe, modify a link, collect another payment or refund anything. Staff's external reconciliation remains their deliberate step. Successfully sent confirmations retain duplicate protection.
- Quotation, invoice and applicable staff top-up invoice Details show any supplied document organisation name and trading name as separate labelled lines. Missing values produce no filler text; when both are absent, Details is blank. The card header continues to show the Account company name.
- Requirements are ordered by `CreatedDate DESC, Id DESC`. Ticking a requirement saves in place and preserves focus/scroll without changing the sort. A lost save response is reconciled with a fresh read: report saved only when confirmed, unsaved only when the opposite value is confirmed, and an uncertain result when neither can be established. A retry does not blindly repeat the mutation.

## Monetary arithmetic and retained checks

Catalogue item prices remain net values, with the existing discount-before-VAT rule. Revised gross totals use inclusive VAT extraction in decimal pence: round the tax component, then obtain net by subtraction. This preserves penny values such as 51p gross / 42p net / 9p VAT that cannot round-trip through the old net-first formula. Saved-total validation accepts the coherent catalogue or inclusive-gross calculation and still rejects inconsistent figures.

The audit retains meaningful safeguards: no negative totals, invalid rates, contradictory itemisation, ambiguous booking references, inactive or uncertain Stripe resources, wrong Stripe account/mode, duplicate successful confirmations, or silent sending to a changed recipient. These are separate from the removed historical-price veto. Stripe's [documented GBP minimum is 30p](https://docs.stripe.com/currencies#minimum-and-maximum-charge-amounts); a positive amount below that needs the bank/manual route. The application's existing conservative upper Stripe amount limit is an implementation limit, not a claim that every card network has that same maximum.

Amounts are not automatically redistributed across the original package or item prices. Intentional itemised recalculation clears the old adjustment; simultaneous manual changes to component fields are still checked as an itemised change. This prevents an Amount edit from hiding unrelated catalogue/pricing-review errors.

## Remaining audit findings and decisions

The following are source-reviewed exception paths, not claims that retained applicants have experienced them. They were not silently converted into new workflow policy. Earlier reports describe the state at discovery; the implemented changes above supersede their Amount/waiver/sort findings.

| Finding | Present limitation and recommended follow-up |
| --- | --- |
| MEX-F01: change an unsuccessful Stripe request to bank transfer | An existing Stripe request can still force the provisional BANK worker down the Stripe route. The current agreed-price receipt path works, but a new bank-transfer provisional message after this switch needs a routing correction that preserves the old request as history and omits its link. |
| MEX-F02 / F03: payment-confirmation recovery | The Opportunity's **Retry booking email** action targets the provisional email. An ordinary failed paid confirmation is recoverable through its record in **NTE Email Failures**. A preparation failure before that dispatch exists may require technical recovery. A single explicit action that creates a missing confirmation or retries its failed dispatch would resolve both, while continuing to refuse resending Sent mail. |
| AUTO-01: editing an already converted Lead | An administrator/API user with converted-Lead edit access could change the form classification out and back, re-entering the conversion copy Flow and overwriting later booking details. Restrict copying to the actual unconverted-to-converted transition. This is source-confirmed; not reproduced against retained records. |
| AUTO-02 / AUTO-03: supplementary-update repair | The current acknowledgement retry is safe. The generic public Apply action is not a safe recovery tool for an already-applied submission because it clears accepted identity/status before processing. A corrected never-applied submission also lacks a clear staff action. Separate safe new intake, reviewed application of a corrected never-applied update, and acknowledgement-only retry. |
| AUTO-04 / AUTO-05: terminal queue/recipient changes | Rare terminal supplementary-job failures can remain Pending without a clear repair path; some recipient-change skips disappear from the failure queue. Expose actionable needs-attention records and inspect exact applied/send history before offering recovery. Do not blindly replay queued work or redirect frozen messages. |
| MEX-I02 and top-up adjustment review: manually changed top-ups | The name-correction form can display catalogue pricing while the backend correctly preserves an already revised top-up amount. Arbitrary aggregate top-up overrides may not divide exactly into a two-decimal unit price. The selected Amount-only adjustment contract covers the base booking; a separate top-up override/display rule should be selected before expanding it. |
| ME04 / ME05: stale/legacy panel state | A failed receipt request can leave stale controls until refresh. A legacy manually entered joining-instructions `Queued` value sits outside the normal sent/unsent refiners. The current manual tick produces the supported values; any legacy-value repair or additional recovery controls should be deliberate. |
| Successful-email resends and additional top-up purchases | A changed booking does not automatically resend a confirmation already sent successfully. There is one accepted positive top-up; same-quantity name corrections remain supported. Additional purchases, reductions or intentional successful-email resends require their own selected workflow rather than clearing history. |
