# Manual exceptions review — automation and recovery

14 September 2026. Internal, read-only review of active source and retained evidence. No source metadata, Salesforce record, provider resource or send was changed or replayed. Preserve all ten NTE-UI and five NTE-INVOICE bookings and completed audit evidence. The root owns the separately approved price-adjusted payment-confirmation change; this report does not propose reinstating that equality check.

## Findings at a glance

| ID | Priority | Finding | Evidence level |
|---|---|---|---|
| AUTO-01 | P1 | An already-converted Lead can re-enter the conversion-copy Flow after form-type reclassification, overwriting manual booking edits. | Confirmed trigger/filter path in source; privileged maintenance reproduction has not been run. |
| AUTO-02 | P2 | The public supplementary apply action resets accepted-update identity/status, allowing an administrative retry to replay old data. | Confirmed public-entry/state transition; ordinary Retry update email uses the safe route instead. |
| AUTO-03 | P2 | Correcting a failed/unmatched supplementary Lead and saving it cannot reapply the corrected data through the available record action. | Create-only Flow plus exact UI/action restrictions. |
| AUTO-04 | P2 | A supplementary worker can leave stale Pending work outside the failure views; its last-resort failure writer also ignores failed save results. | Confirmed recovery/visibility gap; no new native governor-limit or aborted-job reproduction. |
| AUTO-05 | P3 | A legitimate recipient correction can make an unsent message disappear from Email Failures as Skipped, without a direct fresh-draft recovery link. | Existing regression tests explicitly establish the state; send suppression itself is appropriate. |

The practical priority is to prevent replay over newer booking facts, then give staff an explicit route for correcting never-applied submissions. These are different operations from retrying a failed acknowledgement.

## AUTO-01 — Re-entering the conversion Flow can overwrite a manually adjusted booking

The Flow starts when a Lead changes to meet a compound condition: converted, has an Opportunity, and is an exhibitor/partner application. It does **not** require `IsConverted` itself to transition from false to true. The conversion guard explicitly skips a Lead whose previous `IsConverted` value is already true.

**Realistic reproduction:** an administrator with converted-Lead edit permission corrects a historical record classification, temporarily changing an application's form type to another supported non-application type, then restores Exhibitor Application or Partner / Sponsor Application. Its conversion IDs remain unchanged. The second edit changes the Flow predicate from false to true. The Flow recalculates the original application's price and copies its booking details again. A later manual Opportunity adjustment to Amount, itemised prices, billing details, staff allocation or event contacts can be replaced by the old application values. Existing Opportunity payment and communication fields are not reset by that copy, so historical receipt facts can remain beside the reverted commercial facts.

**Source:** [Flow start predicate](../force-app/main/default/flows/NTE_Copy_Converted_Lead_to_Opportunity.flow-meta.xml#L349), [current-price action](../force-app/main/default/flows/NTE_Copy_Converted_Lead_to_Opportunity.flow-meta.xml#L3), [Opportunity assignment block](../force-app/main/default/flows/NTE_Copy_Converted_Lead_to_Opportunity.flow-meta.xml#L38), [guard skips previously converted Leads](../force-app/main/default/classes/NTEConversionGuard.cls#L12). The assignment uses the exact ConvertedOpportunityId, so the failure is overwriting the right booking at the wrong time, not selecting the most recently modified booking.

**Tests:** [normal conversion and older-booking preservation](../force-app/main/default/classes/NTEConversionFlowTest.cls#L433), [no-Opportunity rejection](../force-app/main/default/classes/NTEConversionFlowTest.cls#L582), [existing-booking rejection](../force-app/main/default/classes/NTEConversionFlowTest.cls#L603), and [mixed conversion rollback qualification](../force-app/main/default/classes/NTEManualFinanceTest.cls#L211) cover initial conversion. None tests a previously converted Lead leaving and re-entering the Flow condition. The supplied NTE permission sets grant ConvertLeads but do not themselves grant Edit Converted Leads, so this is an administrator/API maintenance path, not a normal finance-checkbox edit.

**Narrow correction to consider:** make the copy Flow require the actual false-to-true conversion transition as well as the current eligibility checks. Keep the new-Opportunity guard and exact conversion IDs. An explicit future reconciliation tool would need its own reviewed diff; merely editing Lead classification should not act as one. A targeted regression should first change the booking's figures/details manually, exercise converted-Lead reclassification, and assert those fields and payment/email history remain unchanged.

## AUTO-02 — Public apply entry bypasses the safe acknowledgement-only replay guard

[`applyUpdates`](../force-app/main/default/classes/NTEUpdateSubmissionService.cls#L36) is an invocable action named “Apply NTE Supplementary Submission”. Its comment calls it a create-only entry, but the method itself accepts any supplied Lead ID. Lines 48–61 unconditionally write Pending, clear `NTE_Update_Booking_Id__c`, clear applicant/email outcomes, and enqueue processing. By contrast, [`processLeadIds`](../force-app/main/default/classes/NTEUpdateSubmissionService.cls#L174) avoids changing booking data when the saved status is Matched and Applied, and [`retryAcknowledgement`](../force-app/main/default/classes/NTEUpdateSubmissionService.cls#L608) validates the server-saved booking identity before sending only the receipt.

**Realistic reproduction:** a vehicle update was applied, its acknowledgement failed, and staff subsequently corrected the vehicle details directly on the Opportunity. An administrator tries to recover it using the publicly exposed “Apply NTE Supplementary Submission” action. The accepted status and booking identity are erased before processing. The worker now treats it as unapplied and replaces the full vehicle payload using the older submission. If someone also edited its target reference, the saved-identity protection is lost and it can match that new reference. A retained Logo Update can likewise be unnecessarily reapplied, changing update audit timestamps.

**Tests:** [safe retry preserves newer vehicle data](../force-app/main/default/classes/NTEUpdateSubmissionServiceTest.cls#L970) and [an applied receipt cannot be retargeted](../force-app/main/default/classes/NTEUpdateSubmissionServiceTest.cls#L1346) call `retryAcknowledgement` and/or `processLeadIds`, not `applyUpdates` after application. [Create Flow rejects submitted success claims](../force-app/main/default/classes/NTEUpdateSubmissionServiceTest.cls#L1420) correctly requires fresh intake to clear untrusted status/identity. Preserve that protection; the missing distinction is new intake versus a later administrative invocation.

**Exposure boundary:** the maintained supplementary Flow calls this only on Create. The current record action correctly calls the safe retry method. No evidence shows ordinary staff have already triggered this overwrite. The callable entry remains unsafe to recommend as a generic recovery route.

**Narrow correction to consider:** separate authenticated new-intake initialisation from reprocessing a never-applied failed submission and from acknowledgement-only retry. Existing accepted identity/audit must survive any recovery invocation. Add a regression invoking the public action on an already-applied failed receipt with newer Opportunity data. Do not weaken the public-form success-field reset or exact-booking protection.

## AUTO-03 — Corrected never-applied updates have no staff reapply action

The [supplementary Flow](../force-app/main/default/flows/NTE_Supplementary_Update_Handler.flow-meta.xml#L60) runs only on Lead Create. Failed, ambiguous and unmatched records are usefully retained in [NTE Unmatched Updates](../force-app/main/default/objects/Lead/listViews/NTE_Unmatched_Updates.listView-meta.xml). However, the record page offers [Retry update email](../force-app/main/default/flexipages/NTE_Management_Lead_Record_Page.flexipage-meta.xml#L34); its [LWC](../force-app/main/default/lwc/nteRetryEmail/nteRetryEmail.js#L22) calls only `retryAcknowledgement`. That service explicitly requires both Matched and Applied and a Failed applicant email at [lines 629–631](../force-app/main/default/classes/NTEUpdateSubmissionService.cls#L629).

**Realistic reproduction:** a valid staff submission has a mistyped booking reference. It is retained as No Matching Booking. Staff correct the reference on the Lead and save. No worker is scheduled. “Retry update email” rejects it because the booking update has never been applied. The same problem follows a corrected missing declaration or corrected staff-name count. The error text advises correction/retry, but the ordinary action only handles the later email phase.

The source's public `processLeadIds` can process a corrected unapplied record administratively, but that is not an exposed staff action. Using the generic `applyUpdates` entry indiscriminately introduces AUTO-02. The existing [unmatched-reference test](../force-app/main/default/classes/NTEUpdateSubmissionServiceTest.cls#L282) establishes safe rejection; it does not exercise an operator's correct-save-retry journey.

**Recommendation:** select a deliberate “Apply corrected update” route restricted to never-applied records, showing the exact matched booking and current replacement data before applying. Keep acknowledgement retry separate. Do not automatically reapply every Lead edit. P02's rejected-submission recipient/content decision is still unselected; this finding does not authorise emailing form submitters. P07 separately documents the analogous missing failed-intake operator route.

## AUTO-04 — Supplementary Pending work lacks durable terminal-failure recovery

[`applyUpdates`](../force-app/main/default/classes/NTEUpdateSubmissionService.cls#L53) commits a Pending audit and enqueues the job. [`NTEUpdateSubmissionJob`](../force-app/main/default/classes/NTEUpdateSubmissionJob.cls#L11) catches ordinary exceptions but attaches no Finalizer. An uncatchable governor-limit failure in the later transaction can leave the earlier committed Pending status intact. Administrative cancellation before a queued job starts is another stale-Pending case; attaching a Finalizer at worker start alone would not solve that case.

The last-resort [`recordUnexpectedFailure`](../force-app/main/default/classes/NTEUpdateSubmissionService.cls#L67) calls `Database.update(..., false)` but ignores its SaveResults at line 94, then suppresses thrown persistence errors at lines 95–97. It can therefore return without a durable failure audit. The comment mentions concurrent deletion, but the suppression covers any other persistence failure too. A failed temporary-Lead cleanup at [line 299](../force-app/main/default/classes/NTEUpdateSubmissionService.cls#L299) also ignores DeleteResults, leaving accepted temporary records without a cleanup outcome.

**Operational consequence:** Pending is excluded from both the unmatched view (No Matching Booking / Ambiguous Booking Reference / Failed) and the applied-email-failure view. There is no saved AsyncApexJob ID or age-based Pending recovery action here. Staff can mistake invisible unfinished work for a completed queue. The worker's batch acknowledgement cap already records explicit Failed receipts for more than 100 emails; that useful P05 behaviour is separate from this terminal-job gap.

**Tests/evidence:** [unexpected failure helper test](../force-app/main/default/classes/NTEUpdateSubmissionServiceTest.cls#L1700) supplies a synthetic ordinary exception and a successful audit write. It does not fail the queued transaction or the final audit write. The [dispatch worker](../force-app/main/default/classes/NTEEmailDispatchService.cls#L342) and [provisional worker](../force-app/main/default/classes/NTEExhibitorApprovalEmailService.cls#L146) already use Finalizers, providing a project-local comparison. No new native failure was deliberately induced in this audit.

**Recommendation:** persist job identity, expose aged Pending records for inspection, and qualify terminal failure plus failure-audit persistence. Preserve legitimate in-progress work and never blindly replay it; inspect job status and any applied audit before offering the correct recovery action. Record cleanup failures separately from accepted data/email outcomes.

## AUTO-05 — Recipient corrections are safe, but their unsent work needs clearer recovery

An invitation or reminder becomes Skipped when the reviewed recipient/link changes before processing. A failed invitation retried after correcting its email also becomes Skipped. This is intentional and tested: [changed Primary Contact](../force-app/main/default/classes/NTEEmailDispatchServiceTest.cls#L188) and [retry cannot silently switch recipients](../force-app/main/default/classes/NTEEmailDispatchServiceTest.cls#L231). The service tells the operator to prepare a new draft at [retry validation](../force-app/main/default/classes/NTEEmailDispatchService.cls#L301).

However, [NTE Email Failures](../force-app/main/default/objects/NTE_Email_Dispatch__c/listViews/NTE_Email_Failures.listView-meta.xml#L14) filters only Failed. The row therefore leaves that recovery queue, and [history retry availability](../force-app/main/default/classes/NTEEmailDispatchService.cls#L260) is false for Skipped. Its full audit is still available in NTE Recent Emails; it has not been lost. The operator must return to the invitation/reminder workflow and construct another reviewed draft.

**Realistic reproduction:** correct a typo in the Primary Contact email after an unsent reminder was queued, or correct an EOI email after a failed send. No email reaches the corrected address; the old row is Skipped and absent from the failure list. This is recovery friction, not a reason to send a frozen message automatically to a different person.

**Recommendation:** surface actionable “recipient changed; prepare new draft” outcomes in a needs-attention view or direct action, while distinguishing harmless skips for already-completed preparation. Keep the reviewed-recipient/fingerprint checks, successful-history protection and explicit fresh-draft review.

## Cross-review handoffs and policy questions

- **Intake owner reversal — sent to the root/intake reviewer:** [`NTEInboundLeadService` lines 109–115](../force-app/main/default/classes/NTEInboundLeadService.cls#L109) reassign a pending Lead to the configured owner even on a normal retry with `isNewSubmission=false`. A failed internal notice followed by staff reassignment and administrative retry can undo that owner choice. Restricting reassignment to actual new intake is different from removing the currently configured global owner override; the latter has a separate earlier approval boundary. The same service filters converted Leads out at line 65, so recovery after conversion merits the intake reviewer's attention.
- **P01 remains a documentation/behaviour boundary:** the desired workflow still calls paid-booking provisional-retry policy unselected, while the current sender explicitly refuses paid or Closed Lost bookings at [lines 246–247](../force-app/main/default/classes/NTEExhibitorApprovalEmailService.cls#L246). That refusal is consistent with avoiding a new provisional message after confirmation. Do not remove it just to make every retry succeed; select a preparation-only recovery if one is required.
- **Shared Contact role text:** conversion updates “Latest NTE” Account/Contact summary fields intentionally. It also unconditionally writes `Contact.NTE_Contact_Role__c = Applicant / event contact` at [Flow line 345](../force-app/main/default/flows/NTE_Copy_Converted_Lead_to_Opportunity.flow-meta.xml#L345). That plain-text field is not labelled Latest, and the reuse test checks normal identity/contact fields, not a manually curated value there. Clarify whether it is system-owned classification or user-maintained text before changing it. Actual Opportunity Contact Roles are a different object and remain the correct email source.

Recommended validation for any selected follow-up is isolated regression coverage for each exact failure path above, followed by the established affected/full-package checks. No completed live submission, send, receipt, payment or cleanup needs to be replayed to test these guards.
